# 网文整体构建引导（webnovel-guide）

一个网文项目按七个阶段推进：**阶段0 项目体检 → 1 定位策划 → 2 世界观与力量体系 → 3 人物设计 → 4 总纲 → 5 卷纲 → 6 黄金开篇**，之后进入 webnovel-serial 的连载循环。每阶段产出落盘为文件，阶段之间由用户确认推进。

## 核心原则

- **一步一确认**：每阶段先给决策清单（含你的专业建议默认值），用 ask_user_question 逐项收集；确认后才写文件。
- **先读后写**：动笔前读已有文件，从断点续写，不推翻已有成果；沿用项目既有命名与格式。
- **一切落盘**：只有写进文件的设定才算数；会话里的口头共识必须落到对应文件。
- **文件即事实**：后续所有章节的写作与审查，只以工作区文件为准。
- **规格先行**：体量、交付节奏、商业包装类决定（写多长、多少卷、怎么更新、写到哪算完）必须先由用户拍板并落进 `.story-system/project_spec.json`；你只能给带推荐值的选项，默认值须标注「由 AI 代拟」。**没有落盘的规格就是没有规格。**

## 项目目录规范

```
小说项目根/
├─ 设定集/                  # 世界观与人物设定（Markdown）
│  ├─ 世界观.md
│  ├─ 力量体系.md
│  ├─ 主角卡.md
│  ├─ 女主卡.md
│  ├─ 反派设计.md
│  └─ 配角卡/               # 每个重要配角一张卡
├─ 大纲/
│  ├─ 总纲.md               # 一句话故事/主线暗线/卷划分/爽点里程碑/伏笔表
│  ├─ 前30章-留存关卡.md     # 签约关卡 + 节奏关卡的兑现物清单
│  ├─ 第N卷-卷纲骨架.md      # 本卷冲突与卷末高潮倒推
│  ├─ 第N卷-详细大纲.md      # 逐章大纲（含每章 CBN 必需节拍）
│  ├─ 第N卷-节拍表.md        # 每章节拍（beat）
│  └─ 第N卷-时间线.md        # 卷内时间锚点串联
├─ 正文/
│  └─ 第NNNN章-标题.md       # 四位零填充章号
├─ 审查报告/
│  ├─ 第N章审查报告.md
│  └─ 梳理报告-YYYYMMDD.md
├─ .story-system/           # 结构化跟踪台账（机器可查）
│  ├─ project_spec.json     # ★ 项目规格书：体量/交付/包装的唯一事实源（阶段1 产出）
│  ├─ structure_map.json    # ★ 全书结构位置表：百分比锚点 → 章号（阶段6.5 产出）
│  ├─ MASTER_SETTING.md     # 题材/调性/节奏三行基线（人类可读摘要，与 spec 一致）
│  ├─ anti_patterns.md      # 本书禁用反模式清单（持续生长）
│  ├─ fact_registry.md      # 设定与事实词典：名词/事实 | 首现章 | 读者已知 | 完整真相 | 计划揭示 | 状态
│  ├─ chapters/chapter_NNN.json      # 每章元数据（字数/POV/场景/伏笔埋收）
│  ├─ events/chapter_NNN.events.json # 事件流（状态变化/规则揭示/伏笔开闭）
│  ├─ volumes/volume_NNN.json        # 卷级状态（章数与字数预算/卷纲阶段写入并每卷收尾更新）
│  └─ writer_brief.md       # 可选：写手唯一依据任务书（多章批量生产时用）
└─ .webnovel/
   ├─ summaries/chNNNN.md   # 每章 150-300 字剧情摘要（写前快速回读用）
   ├─ idea_bank.json        # 灵感池（未入纲的点子）
   ├─ user-preferences.json # 可选：用户偏好记忆（用于选项排序与 ⭐ 标记）
   └─ state.json            # 当前进度指针（卷/章/下一步）
```

若项目已有等价结构（例如沿用旧跟踪系统的项目），直接沿用其文件名与格式继续，不迁移、不重命名、不推翻。

> **规格优先级**：`.story-system/project_spec.json` 是体量、交付节奏、商业包装的唯一事实源；MASTER_SETTING.md 与总纲.md 若与它冲突，以 spec 为准，并当场向用户报告冲突。

## 阶段0 项目体检（每次会话开始必做）

1. **盘点**：用 glob 列出 设定集/、大纲/、正文/、审查报告/、.story-system/、.webnovel/ 的内容。
2. **判定项目状态**：
   - 空目录或无小说文件 → 新书，从阶段 1 开始；
   - 有文件 → 读 .webnovel/state.json（缺失则从正文与台账推断）确定当前卷、章、断点位置。
2b. **规格体检（强制）**：读 .story-system/project_spec.json。
   - 缺失 且 项目已有正文/大纲 → 规格已丢失，**先补齐规格再继续**（见下方「规格补立」）。
   - 缺失 且 项目为空（全新立项）→ 正常，阶段1 必须产出。
   - 存在 → 校验 spec 与 MASTER_SETTING.md / 总纲.md 是否一致；不一致立刻报告。
3. **呈现体检报告**：已完成阶段、当前断点（写到第几卷第几章/大纲做到哪）、台账缺口（如正文存在但缺 summaries 或 events）、规格缺口。
4. **台账补齐**：对已有正文补建 summaries 与 events（可分派 subagent 并行处理各章，主会话汇总核对）。
5. **确认下一步**：继续连载 / 先做一次 webnovel-audit 梳理 / 补某阶段缺失文件。

### 规格补立（老项目缺 spec 时的补救流程）

1. 从现有 MASTER_SETTING.md / 总纲.md / state.json / 正文 反推出**候选规格**（章长、平台、已写章数、已写字数）。
2. 用 ask_user_question 让用户拍板缺失项：总字数、总章数/总卷数、单章字数、更新频率、目标完本周期、结局基调、创作主导权。
3. 写 .story-system/project_spec.json，在 `inferred_from` 里标注反推来源（如 `大纲/总纲.md:40`），并写 `confirmed_at` / `confirmed_by`。
4. 在 审查报告/ 留一份《规格补立说明》，记录哪些字段是反推的、哪些是用户拍板的。

## 阶段1 定位策划

分两轮确认，不要一口气甩一张大表单。**1B 不可跳过**——体量与交付规格缺任一项，阶段1 视为未完成，不得进入阶段2。

### 1A.0 交互规范（约束你怎么问，不只是问什么）

- **轮次密度**：单次 ask_user_question 最多 4 问，全程 ≤14 问；尽量合并提问，减少打断轮次。
- **选项结构**：每问 ≤4 个选项且 ≥2 个；"Other/我自己写"是内置自由输入入口，不占选项位。
- **永不堵死**：每问都接受"跳过 / 🎲 随机生成"。跳过时你代拟，但必须在摘要卡里标注「由 AI 代拟」。
- **快捷入口检测**：用户首句已含足够信息（题材+主角+冲突+体量）时，先展示你提取到的内容，问 3 选项：「按这个开始」/「先让我改」/「重新走一遍」——不要重复问已给的信息。
- **收口唯一**：1A+1B 全部问完 → 输出一张《创作规格确认卡》（见下）→ 只问一次"确认无误吗？"，确认后写入 project_spec.json 并标记 `locked:true`。之后任何规格变更必须走"解锁流程"并留痕。
- **可回退**：用户说"重新问 XX / 改 XX" → 只重问该项，已确认的不重复问。
- **偏好记忆**：每完成一轮，静默把选择同步到 .webnovel/user-preferences.json，用于下次选项排序与 ⭐ 标记。
- **归属标注**：每一个落盘字段都标 `source: user | ai_default | inferred`，区分"作者事实"与"AI 推断"。

### 1A 内容定位（题材 · 卖点 · 读者）

- **题材赛道**：主题材 + 副题材及配比（如 7 玄幻 + 3 规则怪谈）。
- **目标平台与读者画像**：起点/番茄/晋江等 + 频道（男频/女频）+ 免费还是付费 + 目标读者画像 + **对标作品 2-3 本**（同类火书横向对比，是"写法"判断的核心方法）。
- **一句话故事**：≤50 字，含主角身份 + 金手指 + 核心冲突 + 差异化卖点。
- **金手指设计三问**：有代价吗（代价即张力）？能成长迭代吗（撑起全书的升级线）？与主线冲突强绑定吗？
- **反套路约束**：本书刻意避免的俗套，写成 anti_patterns.md 初始清单。
- **调性基线**：题材/调性/节奏三行，写进 MASTER_SETTING.md。
- **结局基调**：圆满 / 开放 / 悲剧——开书前必须定。
- **主题**：一句话，作为主题漂移的锚。

### 1B 体量与交付规格（★ 开书前必须拍板）

每项都要给**推荐默认值 + 常见区间**，让用户做选择而不是填空。

| 字段 | 常见取值 | 说明 |
|---|---|---|
| **目标总字数（预计完结字数）** | 40–50万 / **100万（付费长篇基础需求）** / **200–300万（付费主流）** | 官方投稿环节的必填项；纵横合同按字数区间分档 |
| **目标总章数** | 由总字数 ÷ 单章字数推导 | 必须与总字数自洽 |
| **总卷数** | 3–8 卷 | 每卷 = 一个卷末高潮 |
| **每卷章数 / 每卷字数** | 20–60 章；**每卷 ≤ 40 万字** | 官方分段法：一段剧情 10–20 万字 |
| **单章字数** | 番茄 1500–2500 / 起点 2000–3000 / 晋江 3000–5000 | 平台决定，不可自相矛盾 |
| **更新频率** | 日更 1 章 / 2 章 / 3 章 | |
| **日更字数（保底）** | 3000 / 6000 / 8000+；**纵横全勤线：日更 ≥4000（进阶 ≥6000）** | 官方明码标价的硬指标 |
| **月更字数** | ≥12 万 / ≥18 万 | 纵横全勤口径 |
| **目标完本周期** | 由 总字数 ÷ 日更字数 推算（月） | 推不动就说明总量或更新量要改 |
| **存稿量目标** | 3–5 万字缓冲（约十章精修） | 防断更；官方"准备期 2–4 个月" |
| **断更/请假预案** | 每月请假 1 天；断更 15 天 / 30 天的后果 | 官方惩罚线 |
| **开书准备期** | 大纲+素材+存稿的投入周期（周/月） | |
| **首月里程碑** | 上架/签约节点：第几章、什么数据触发什么动作 | |
| **签约关卡** | 黄金 **3** 章（可 3/4/5 章） | 官方："三章决定签不签约" |
| **节奏关卡** | 前 **20–30 章** / 前 **10 万字** | 官方："三章不能决定出不出成绩" |
| **留存指标目标** | X 万字留存 ≥8–12% + 日阅读 UV ≥100→3000 | 纵横官方门槛表口径 |
| **节奏核心（按题材）** | 升级流=每隔 N 章升级；历史流=大事件起止；竞技流=赛程 | 官方作者口径：节奏＝"每隔多少章给主角一次提升" |
| **爽点密度** | 每章 ≥1 小爽点；每 N 章 ≥1 大爽点 | |
| **商业包装** | 书名候选 **3–5 个**、150 字简介、标签/关键词、封面金句 | 官方编辑明说"备选书名至少3–5个" |
| **平台 AI 政策** | 该平台是否允许 AI 辅助 / 拒绝 AI 内容的条款 | ⚠️ 阅文明示"拒绝 AI 生成内容，查实后无法签约" |
| **平台规则清单** | 全勤线 / 推荐机制 / 读者口味 / 字数区间上限 | 官方作者口径："都要了解清楚，不然写了半天网站不给推荐" |
| **创作主导权** | ① AI 代写+我审 ② 我写正文+AI 当编辑核对 ③ 分段共写 | **必答、不可默认**；默认代写＝替用户选了主导权 |
| **风格负面清单** | 禁用套句（"眼中闪过一丝"…）、禁章末总结句、禁数据罗列灌水 | 对治 AI 味；落进 anti_patterns.md |
| **结局基调** | 圆满 / 开放 / 悲剧 | 官方开书六步明列"结局是否圆满" |
| **大纲承诺边界** | 本次大纲写到第几卷 | 官方建议"第一卷写实，第二卷待定" |
| **合规红线** | 平台审核禁区 + 本书主动规避项 | 写进 anti_patterns.md |

**体量自洽校验（当场算给用户看）**：
- `总字数 ≈ 总章数 × 平均章长`（容差 ±10%）
- `完本周期(月) ≈ 总字数 ÷ 日更字数 ÷ 30`
- `总章数 ≈ 总卷数 × 每卷章数`

三条对不上就当场指出并给修正选项，不许带着矛盾进入下一阶段。

**《创作规格确认卡》模板（收口时输出一次）**：
```
## 创作规格确认
📖 题材：[X] — [一句话故事]
🧑 主角：[设定] ｜ 缺陷：[ ] ｜ 驱动力：[ ]
💥 核心冲突：[ ] ｜ 🎯 结局基调：[ ] ｜ 💡 主题：[ ]
🌍 世界/力量体系：[ ] ｜ 👁 视角：[ ] ｜ 🎨 基调：[ ] ｜ 📚 读者：[ ]
📊 规模：[总字数] 字 / [总章数] 章（每章 [ ]） / 分 [N] 卷（每卷 [ ] 章）
⚡ 日更：[ ] ｜ 🗓 完本周期：[ ] 月 ｜ 💾 存稿目标：[ ] 万字
🎯 签约关卡：前 [3] 章 ｜ 节奏关卡：前 [20-30] 章 / 前 [10] 万字
```

**产出**：
- 大纲/总纲.md（故事一句话 + 创意约束段）
- .story-system/MASTER_SETTING.md（题材/调性/节奏三行 + 平台与读者 + 一句话故事 + 金手指三问 + 硬约束）
- .story-system/anti_patterns.md
- **.story-system/project_spec.json**（体量/交付/包装/里程碑/创作主导权/合规的唯一事实源；字段与《黄册》回填示例见 审查报告/agent改进/patch-B-project_spec.schema.md）

## 阶段2 世界观与力量体系

- **世界结构**：界/势力/关系图；势力间的矛盾如何直接制造主线冲突（世界观不为背景板）。
- **力量体系**：等级阶梯、能力来源、**代价与限制**、升级路径。规则必须可执行、违规必有后果；写不出来执行细节的规则不要写。
- **与金手指的关系**：金手指在世界观中的位置、排异性、被世界规则反噬的可能。

产出：设定集/世界观.md、设定集/力量体系.md、**.story-system/fact_registry.md**。

**事实登记两条铁律**（同时写进 anti_patterns.md 与 writer_brief.md）：
1. **先登记后动笔**：正文里要写的任何数字、口径、专名、伏笔，fact_registry 里没有的，必须先登记再写——"三套时间线对不上，几乎都是各章现场编数导致的"。
2. **到期必兑**：登记了「计划揭示」的条目，写到该章必须兑现并更新「读者已知」栏；决定放弃的登记为「弃用」，**不得悬空**。

fact_registry 字段：名词/事实 | 首现章 | 读者已知 | 完整真相 | 计划揭示 | 状态。

## 阶段3 人物设计

- **主角卡**：身份/性格/核心缺陷/动机/成长弧线（起点状态 → 关键跃迁节点 → 终局定位）/语言习惯。
- **女主卡**（或感情线设计）：与主线的结构性关系，不做挂件。
- **反派分层**：小反派（卷内 BOSS）/中反派（跨卷代理人）/大反派（全书意志），尽量与主角镜像。
- **配角卡**：每人一个明确剧情功能。

产出：设定集/主角卡.md、女主卡.md、反派设计.md、配角卡/*.md。

## 阶段4 总纲

- **核心主线**（目标 + 阻力）、**核心暗线**（主题 + 分层回收节点）。
- **卷划分表**：卷号/卷名/章节范围/核心冲突/卷末高潮/本卷换了什么（地图·境界·副本·身份）。
- **主角成长线**、**关键爽点里程碑**（章号区间 + 事件 + 爽点类型）。
- **伏笔表**：内容/埋设章/回收章/层级（主线/副线/长线/卷末钩子/持续开放环）。

产出：大纲/总纲.md 完整版。

### 阶段4 收尾：体量对账（强制）

卷划分表写完后，立刻与 project_spec.json 对账：
1. `Σ(每卷章号区间长度) == target_chapters`？
2. `Σ(每卷章数 × 平均章长) ≈ target_words`（容差 ±10%）？
3. `卷数 == spec.scale.volumes`？

- 全部通过 → 在总纲.md 的卷划分表下方加一行"体量对账：✅ 与 project_spec 一致"。
- 任一不通过 → **带着差异数据找用户拍板**（改卷划分，还是改规格），不许静默通过、不许只改一边。

## 阶段5 卷纲（以卷为单位，写完一卷再做下一卷）

- **卷纲骨架**：从卷末高潮**倒推**——卷末状态 → 必需转折 → 必需铺垫 → 开卷钩子。
- **详细大纲**：逐章条目（每章：目标/主要场景/出场人物/埋收伏笔/章末钩子/CBN 本章必需节拍）。
- **节拍表**：每章 3-5 个 beat。
- **时间线**：卷内时间锚点串联。

### 卷级预算与卷的语义（强制字段）

每卷卷纲骨架必须写明并入库 .story-system/volumes/volume_NNN.json：
- `chapters_count`：本卷章数
- `words_budget`：本卷目标字数（≈ chapters_count × 平均章长）
- `start_chapter` / `end_chapter`：与总纲卷划分表完全一致
- `volume_pivot`：**本卷换了什么**（地图 / 境界 / 副本世界 / 身份 / 势力格局）——一句话
- `volume_units`：本卷包含几段独立剧情（每段 1–3 万字），各自的起止章

> 卷的划分口径不是"多少章一卷"，而是**空间转场**：网文"通过空间转场来设定大纲、通过换地图来打怪升级、通过开副本来拓宽情节场景"。只按章号平均切分会让中段密度塌陷。`volume_pivot` 是可机检字段——audit 会校验"连续两卷的 pivot 是否真的不同"。

写完一卷再写下一卷；每卷收尾时用实际字数回填 `words_actual`，偏差 >10% 触发进度告警。

产出：大纲/第N卷-卷纲骨架.md、第N卷-详细大纲.md、第N卷-节拍表.md、第N卷-时间线.md 四件套，以及 .story-system/volumes/volume_NNN.json（卷目标/卷内章号区间/卷末高潮/卷级预算/volume_pivot/当前状态）。

## 阶段6 黄金开篇与前 30 章留存设计

### 6.1 黄金开篇（前三章 · 签约关卡）

- **第 1 章**：主角身份 + 世界异常 + 入戏钩子（前 300 字必须抓人）。
- **第 2 章**：金手指亮相 + 第一次小爽点。
- **第 3 章**：确立追读理由——大悬念 + 期待感 + 主角魅力。
- 前三章经 webnovel-serial 流水线写完后，与用户逐章复盘打磨，再进入常规连载。

### 6.2 前 30 章留存关卡（节奏关卡）

> 三章只决定签不签约，不决定出不出的成绩——两个关卡必须分开设计。

| 关卡 | 必须兑现 | 检查点 |
|---|---|---|
| 第 1 章 | 主角身份 + 世界异常 + 入戏钩子 | 前 300 字抓人 |
| 第 3 章 | 金手指亮相 + 首次小爽点 + 核心承诺可见 | "这书值不值得追"（**签约关卡**） |
| 第 10 章 | 第一个完整单元案闭环 | 目标读者确认口味 |
| 第 20 章 | 第一次地位/实力跃迁 | 爽点升级 |
| 第 30 章 | 第一卷高潮 + 下一卷拉力 | 卷末留人（**节奏关卡**） |

产出：大纲/前30章-留存关卡.md（每关卡：兑现物 / 章号 / 钩子 / 未兑现承诺清单）。

> 开书前就要"确定小高潮、大高潮落在哪几章"。

## 阶段推进协议

- 阶段开始 → 给决策清单 + 建议默认值 → ask_user_question 逐项收集。
- 阶段结束 → 产出文件 + 阶段小结（定了什么/放弃了什么/对后续的承诺）→ 预览下一阶段 → 用户确认才推进。
- 用户回改某阶段 → 先更新该阶段文件，再检查对下游文件的影响并同步修订。
- **分轮**：单轮 ask_user_question 控制在 3-4 个问题以内，分 2-3 轮收完一个阶段的决策；用户说"你定"才采用默认值，并标注「此为 agent 决定」。
- **落盘**：每轮确认完立刻写盘（spec / 设定 / 大纲），不等阶段结束——会话记忆会丢，文件不会。
- **摘要卡收口**：一个阶段的决策收完，输出一张该阶段的摘要卡并问一次"确认无误吗？"，确认后再推进下一阶段。
- **回退**：用户说"重新问 XX"只重问该项，不重复问已确认的项。
